# Spammer — конвейерная обработка писем на Go

Учебное задание с курса **VK Education по веб-разработке на Go**, тема «Асинхронное программирование».

Задача — реализовать аналог unix pipeline на каналах:

```
cat emails.txt | SelectUsers | SelectMessages | CheckSpam | CombineResults
```

На вход подаются email'ы пользователей, на выходе — список их писем с пометкой, спам это или нет. Все этапы работают одновременно, поэтому вся цепочка укладывается в ~3 секунды, хотя отдельные вызовы «сервисов» занимают от 100 мс до 1 с.

## Структура

| Файл | Описание |
|---|---|
| `spammer.go` | Моё решение |
| `common.go` | Заготовка от авторов курса: типы и функции-«сервисы» (`GetUser`, `GetMessages`, `HasSpam`) |
| `main_test.go` | Тесты от авторов курса |

## Что реализовано

### `RunPipeline(cmds ...cmd)`

Связывает функции-этапы в конвейер. Каждый этап запускается в своей горутине, выходной канал одного этапа становится входным для следующего. Когда этап завершается, его выходной канал закрывается — так следующий этап узнаёт, что данных больше не будет. Функция ждёт завершения всех этапов через `sync.WaitGroup`.

### `SelectUsers`

Получает email'ы и отдаёт уникальных пользователей.

- `GetUser` выполняется 1 секунду, поэтому на каждый email запускается отдельная горутина — все запросы идут параллельно.
- У некоторых пользователей есть алиасы (`batman@mail.ru` → `bruce.wayne@mail.ru`). Дубликаты отсекаются по `User.ID` через `map`, защищённую `sync.Mutex`.

### `SelectMessages`

Получает пользователей и отдаёт ID их писем.

- `GetMessages` принимает до 2 пользователей за вызов. Пользователи собираются в батчи по 2, и батч отправляется в отдельной горутине сразу, как только заполнился, не дожидаясь остальных.
- Если пользователей нечётное число, оставшийся отправляется отдельным вызовом.
- Количество вызовов `GetMessages` минимально возможное — это проверяется тестами.

### `CheckSpam`

Проверяет каждое письмо через `HasSpam`.

- Сервис антиспама возвращает ошибку при более чем 5 одновременных запросах.
- Параллельность ограничена семафором на буферизованном канале ёмкостью 5: горутина занимает слот перед запросом и освобождает после.

### `CombineResults`

Собирает все результаты, сортирует их (сначала спам, затем по возрастанию ID) и отдаёт строки вида `true 17696166526272393238`. Этому этапу параллельность не нужна: он в любом случае ждёт все данные перед сортировкой.

## Использованные инструменты

- горутины и каналы
- `sync.WaitGroup` — ожидание группы горутин
- `sync.Mutex` — защита общей `map` от гонок
- семафор на буферизованном канале — ограничение числа параллельных запросов
- приведение типов из `interface{}` (type assertion)

## Запуск тестов

```bash
go test -v -race
```

Флаг `-race` включает детектор гонок данных. Он работает только на 64-битном Go; на Windows для него нужен gcc, поэтому удобнее запускать в WSL. По условию задания на Windows без WSL даже корректное решение может немного не укладываться в лимит по времени.
